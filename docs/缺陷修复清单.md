## D-01 模型输出协议强校验（已修复）

`ModelOutputProtocol` 原先强制 `summary/tags/cards/relations` 四字段齐全，而提示词要求「无关联不输出 relations」，两边契约相反，导致任务 100% 报 `MODEL_OUTPUT_INVALID`。
现为「仅当检索候选为空且缺 relations 时补空数组」，有候选时仍严格拒绝。实测 `candidate_json.relations=0`，容忍分支命中。

## D-02 缺必填参数返回 500（已修复）

`ApiExceptionHandler` 新增 `MissingServletRequestParameterException` → 400 `BAD_QUERY`「缺少必填查询参数：version」，无副作用。

## D-03 前端测试大面积失败（已修复）

测试 require 白名单补齐 `element-plus`，Dialog 语义适配器处理插槽/关闭/提交锁定。`node --test` 304/304。
遗留说明：适配器不是真实 Element Plus，关键交互仍以真实浏览器验证为准，答辩时按「测试局限性」表述。

## D-04 后端测试 flaky（已修复）

**根因**：`TaskLeaseServiceImpl.claim()` 取到过期任务后清理完直接 `return null`，不再取下一条。前序测试遗留的过期任务会吞掉本次领取，调用方解引用即 NPE。
**修复**：改为最多 3 次重试的循环，超时清理与领取失败都用 `continue` 续取，只有队列真正为空才返回 null。
**验证**：`mvn -o -f backend/pom.xml verify` 连续两次 330/330、BUILD SUCCESS（修复前首次 clean 必现 1 error）。

## D-05 404/405/415 全被兜底成 500（已修复）

`ApiExceptionHandler` 新增三个映射，并把兜底日志的异常对象补上（此前只打类名，堆栈丢失）：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `GET /api/v1/does-not-exist` | 500 `INTERNAL_ERROR` | 404 `NOT_FOUND` |
| `PUT /api/v1/materials` | 500 `INTERNAL_ERROR` | 405 `METHOD_NOT_ALLOWED` |
| `POST /api/v1/materials` + `text/plain` | 500 `INTERNAL_ERROR` | 415 `UNSUPPORTED_MEDIA_TYPE` |
| `POST /api/v1/ai-tasks/999999/cancel`（单数） | 500 `INTERNAL_ERROR` | 404 `NOT_FOUND` |
| `POST /api/v1/ai-tasks/999999/cancellations`（复数） | 404 `TASK_NOT_FOUND` | 404 `TASK_NOT_FOUND`（不变） |

405/415 响应保留 `Allow`、`Accept` 头。

## D-06 审核无失效机制（已修复）

**原缺陷**：资料审核通过后再修改正文，`content_review` 仍 `APPROVED`、`material.access_state` 仍 `NORMAL`，改过的内容继续可被检索与卡片引用，等于绕过审核。

**修复内容**：
1. `V18__content_review_supersede.sql`：给 `content_review` 加 `superseded_at`，CHECK 约束扩展 `SUPERSEDED`，`notification.chk_notification_target` 扩展 `REVIEW_SUPERSEDED`，并一次性修正存量脏数据。
2. `ContentReviewMapper.supersedeByMaterial()`：把该资料 `PENDING/APPROVED` 的记录置 `SUPERSEDED`，记 `superseded_at`、`version+1`。
3. `ContentReviewServiceImpl.supersedeByMaterial()`：`Propagation.MANDATORY`，同一事务内联动 `access_state=RESTRICTED`、取消该资料在跑的 AI 任务、把 RUNNING 的工具/OCR/模型尝试标 `SOURCE_RESTRICTED`、插 `REVIEW_SUPERSEDED` 站内通知。
4. 三个联动点：`MaterialServiceImpl.update`、`MaterialServiceImpl.delete`、`TaskConfirmationServiceImpl.confirm`（AI 确认改动正文）。
5. 查询与展示：`list()` 状态白名单加 `SUPERSEDED`；`ReviewView` 增 `isCurrent`/`supersededAt`；前端审核列表加筛选项，用户侧显示「已失效，需重新送审」、失效时间与「旧版本授权已失效」。

**本机实际验证（库 `learning_material_dev`，资料 8 / 审核 3、4）**：

| 步骤 | 结果 |
|---|---|
| 新建笔记 v1 → 送审 → 管理员批准 | `material.version=1, access_state=NORMAL`；`review 3=APPROVED` |
| PATCH 正文（v1→v2） | `access_state=RESTRICTED`；`review 3=SUPERSEDED`，`superseded_at=2026-10-30 14:24:04`；生成通知 13 `REVIEW_SUPERSEDED` |
| 再次送审 v2 → 批准 | `review 4=APPROVED`，`access_state` 恢复 `NORMAL` |
| 管理员 `?status=SUPERSEDED` | 命中 2 条（存量 review 2 + 本次 review 3） |
| 用户审核历史 | `4 APPROVED isCurrent=true`、`3 SUPERSEDED isCurrent=false` |

存量脏数据也已被 V18 修正：资料 4（v3，旧批准针对 v2）现为 `RESTRICTED`，其审核单转 `SUPERSEDED` 并通知作者；资料 1（v2，批准针对 v2）保持 `NORMAL`，未误伤。
