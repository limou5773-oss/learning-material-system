# 个人学习资料智能整理系统数据库设计

设计基线V1.0，2026年10月22日；实现说明更新于2026年10月26日。依据开题报告整理的开发建议，共18张拟议表。`app_user`、`auth_session`、`material`、`tag`和`material_tag`通过V1至V3迁移实现，`favorite`的资料收藏部分通过V4实现，`ai_task`与`ai_tool_call`通过V5实现，`material_chunk`与`ai_result`通过V6实现，`knowledge_card`、`card_source`与`card_relation`通过V7实现。其余拟议表未执行。下表保留设计基线，实际DDL以`backend/src/main/resources/db/migration/`为准；《拟议建表.sql》仅供设计参考，不得整份导入运行库。业务规则以《需求与开发说明书.md》为准。

D12时的V7仅支持从任务确认生成卡片：`task_id`、`candidate_key`、`tags_json`为非空，正文为TEXT；`generation_mode`单独保存MOCK标识，避免将模拟结果混作真实模型输出。卡片来源的引用与起止位置均非空，唯一键为`(card_id,chunk_id,start_offset,end_offset)`，允许同片段不同摘录。关系增加`origin=USER_CONFIRMED`。D17的V12补充人工卡片，完整关系管理仍在后续阶段实现。

D13的V8增加基线之外的`pdf_page_cache`支持表。`material_chunk.extraction_method`扩展为PDF_TEXT，`page_no`保存实际页码；旧NOTE及METADATA片段保持不变，历史引用不会重新生成或覆盖。

通用字段：id为BIGINT自增主键；created_at和updated_at为DATETIME，约定保存UTC。所有ID在API中序列化为字符串，JSON时间带Z。通用字段不在各表重复列出。

索引中的外键只约束引用存在；所有者一致性、关系方向、层级无环、版本冲突、任务状态及幂等摘要必须在服务层验证。没有ON DELETE CASCADE，删除采用业务逻辑状态。

## 19 pdf_page_cache PDF页级提取缓存（V8新增）

| 字段 | 类型 | 可空 | 含义 |
| --- | --- | --- | --- |
| material_id | BIGINT | 否 | 来源资料，FK到material.id |
| material_version | INT | 否 | 固定资料版本 |
| page_no | INT | 否 | 实际PDF页码，从1开始 |
| total_pages | INT | 否 | 原文件实际总页数 |
| extraction_status | VARCHAR(16) | 否 | TEXT或NEEDS_OCR；无文字层也可能是空白页 |
| page_text | LONGTEXT | 否 | 本页文字层全文；无文字页为空串 |
| created_at | DATETIME(6) | 否 | UTC缓存时间 |

唯一键为`(material_id,material_version,page_no)`。首次解析在持锁事务外完成；发布时按资料→任务加锁，复验权限、访问状态、版本、文件标识及有效租约/epoch，缓存与来源原子写入。冲突只复用一致的缓存，不覆盖旧值。

PDF片段编号为`2_000_000 + pageNo * 100 + partIndex`（partIndex从0开始），避开NOTE编号1—3和METADATA编号1_000_000；同版本重叠页段保持chunkId一致。每块最多2000个UTF-16代码单元且不拆开代理对，单任务最多30块和60000个文本代码单元；超限明确失败，缓存不发布部分结果。NEEDS_OCR页不生成伪原文来源。

## 20 事务与数据生命周期

任务提交、候选确认、用户停用、审核处置分别建立短事务。外部OCR和模型请求不能处于数据库持锁事务中。确认操作锁定任务与源资料，保证卡片、来源、所选关系、正式摘要、标签及最终状态整体提交。

资料逻辑删除后片段只用于受控历史一致性，不允许通过卡片来源重新读到已删除原文。正式卡片可以保留来源失效提示，此时CardSource的quoteText与content都返回null。布局、收藏和图查询过滤已删除卡片。管理员受控查看资料必须记录CONTENT_VIEW。

ai_task.config_json保存本次页段、预算、输入快照、模型和OCR标识及同意时间。material_chunk按版本缓存；worker写入必须在持有task行锁并验证epoch的短事务内完成，防止过期执行者修改片段或结果。

实际V7的card_source按卡片、片段和摘录区间去重，同片段可有不同摘录。offset沿用D11的Java字符串UTF-16代码单元计数，起始包含、结束不包含；例如辅助平面字符占两个代码单元。服务端校验引用等于该区间原文，并限制为原候选允许的固定版本片段。RELATED关系按较小ID为起点规范化，反向重复在写入前拒绝；PREREQUISITE表示起点为终点的前置知识，EXAMPLE表示起点为终点的示例。来源被删除或受限时，读取接口将quote_text和片段正文置空，附不可用原因。

所有NOT NULL字段由应用明确赋值。SQL仅包含时间默认值，不将配置中的枚举和初始版本隐藏为数据库隐式行为。Flyway等迁移工具在初始化时选定并锁定版本，按用户笔记、文件、任务、卡片、管理等开发阶段分批建表。

## D14：V9 OCR缓存与请求尝试

以实际迁移`V9__create_ocr_cache_and_attempt.sql`为准。新增两张支持表：

| 表 | 唯一键/关键字段 | 用途 |
| --- | --- | --- |
| ocr_page_cache | material_id、material_version、page_no；provider_key、extraction_status、page_text、confidence、request_id | 图片page_no=0，PDF为真实页码；TEXT/EMPTY均缓存，同版本同页不覆盖，厂商/预处理版本冲突明确失败 |
| ocr_attempt | task_id、page_no、attempt_no；execution_epoch、provider_key、dispatched、status、error_code、request_id、started_at、finished_at、duration_ms、cost | 每次调用独立记录；RUNNING/SUCCESS/FAILED/UNKNOWN，单页最多2次、每任务最多20次，跨租约接管累计预算 |

`dispatched`表示可能已发出请求，不表示供应商已成功处理或实际账单次数。取消、删除或租约失效时，进行中尝试保留为UNKNOWN；`cost`未知为NULL，不能统计为0费用。`ai_tool_call`是工具动作记录，不能直接当成OCR请求次数。缓存命中不新增外部请求。

OCR来源`chunk_no=3_000_000+pageNo*100+partIndex`，图片pageNo为空；每块最多2000个UTF-16代码单元、总30块/60000单元。质量说明保存在material_chunk.quality_note，确认保存后的卡片来源接口保留方式与说明；来源失效时隐藏正文、引用和质量说明。外部请求及PDF渲染在持锁事务之外执行，发布前重新验证资料、用户、文件快照、任务租约与epoch。

## D15：V10模型请求记录

以实际迁移`V10__create_model_attempt.sql`为准。`model_attempt`按(task_id,attempt_no)唯一，保存execution_epoch、provider_key、requested_model、response_model、prompt_version、request_id、input_tokens、output_tokens、dispatched、status、error_code、起止时间、duration_ms及cost。每任务最多两次尝试，跨epoch累计；未知token数和费用保持NULL。状态RUNNING/SUCCESS/FAILED/UNKNOWN，dispatched表示可能已发出，不等于厂商实收或已计费。

取消、删除和租约恢复使进行中记录为UNKNOWN；旧worker自己的清理按task+epoch隔离。外部请求与提示构造不持数据库锁；调用与发布前复验用户ENABLED、所有权、来源版本、访问、输入/文件快照及任务租约。模型结果校验后只保存ai_result候选并进入WAIT_CONFIRM，正式卡片仍由已有确认事务原子保存。

`ai_result.candidate_json`新增可空generationInfo(provider/model/promptVersion)，MOCK旧记录兼容；MODEL由服务端赋值，模型不能自报模式或任务ID。正式卡片沿用generation_mode字段区分MOCK/MODEL，模型元数据保留在候选和请求记录中，不虚构旧卡片的供应商信息。模型来源引用只允许本次提交的固定版本片段，UTF-16 offset由服务端精确匹配原文计算。

## D16：V11规划与生成用量区分

以`V11__add_agent_model_attempt_purpose.sql`为准，model_attempt增加purpose，原记录默认为GENERATION，规划请求为PLANNER；编号约束扩展至最多8。D15 model模式仍由业务限制最多2次；D16 agent最多8次合计、4次规划、2次生成，跨epoch累计。purpose不改变UNKNOWN、已知token保留及未知费用NULL的约定。

ai_task.config_json记录processorMode及预算，模式/模型改变时明确拒绝，不静默替换；旧mock/model配置按既有兼容约定处理。ai_tool_call记录planner与工具动作、目标和受控反馈摘要，8步预算包括planner，不保存模型隐藏思维。

个人检索从knowledge_card及其来源关系做参数化关键词召回；筛除非本人、已删卡片及来源已删/受限卡片，最多10条，片段最多1200个UTF-16单元并标明截取，不新增向量或图数据库。agent候选仍复用ai_result/CardRelation契约，主引用只指向本次主资料，关联目标只来自本轮召回并保留版本。

候选发布和关系确认事务先将主资料与关联来源material合并，按ID统一预锁，再锁任务及相关card并检查当前权限、版本，避免两任务互相关联时形成交叉锁环。正式卡片、所选关联及资料摘要仍由已有确认事务原子保存；检索权限错误和版本变化明确失败，不把数据库错误当成无搜索结果。

## D17：V12人工卡片与卡片收藏

人工卡片的`origin`及`generation_mode`均为MANUAL，`task_id`与`candidate_key`为NULL，不伪造任务或来源。AI确认所得卡片保留AI来源、MOCK/MODEL模式及任务候选唯一键。既有V7不改写，实际放宽与约束见V12迁移。

新建卡片version=1、is_edited=false；后续人工编辑使用版本校验并在成功时version+1、is_edited=true，保留模式、来源、关系与父节点。冲突返回409及当前版本，不覆盖他端内容。人工卡片来源列表为空；AI来源仍为创建时的固定历史片段，编辑正文不重写引用。编辑卡片会使D16中已召回的旧卡片版本失效，继续沿用明确冲突检查。

复用favorite的card_id和(user_id,card_id)唯一键，补充knowledge_card外键。添加收藏先校验本人未删除卡片，重复添加/移除幂等，不递增内容版本。收藏列表可按MATERIAL/CARD筛选，省略类型时统一按收藏时间与ID分页；卡片视图的favorite由当前账号收藏关系计算。关键词使用参数化包含匹配，学科、标签精确匹配，仅查询本人未删除卡片，不引入搜索服务或额外索引体系。
