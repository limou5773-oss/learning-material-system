# D13 真实PDF片段提取

日期：2026年10月25日。状态：实现、自动化、Web浏览器与小程序页面真实HTTP验证完成；微信开发者工具原生流程继续按用户此前决定暂缓。

## 实现

- 复用已锁定的Apache PDFBox 3.0.8，从本人已上传PDF的所选连续页段提取真实文字层，最多20页。只通过服务端FileStorage受控存储键访问文件，不接收任意路径。
- V8新增`pdf_page_cache`，按资料ID、资料版本、页码唯一保存完整页文字、实际总页数及TEXT/NEEDS_OCR状态。无文字页也缓存；同版本重叠页段复用缓存及chunkId。旧缓存与来源只复用，不覆盖。
- PDF解析在持锁事务外执行。发布缓存及来源时按资料→任务加锁，复验所属用户、访问状态、资料/任务配置与版本、存储标识、RUNNING、取消标记、epoch及有效租约。失效执行者不能写入。
- 来源采用PDF_TEXT与真实pageNo，稳定编号保留区域避开原有NOTE和METADATA。每块最多2000个UTF-16代码单元，不切开代理对；每任务最多30块和60000个文本代码单元。超限明确失败并提示缩小页段，不保存截断的PDF文字。
- PDF走`extract_pdf_text`本地工具步骤，参数白名单校验资料、版本和页段；错误步骤明确记为FAILED。混合PDF的warnings列出无文字页，processedPages只包含有效文字页；全范围无文字报PDF_OCR_REQUIRED，不用标题冒充原文。
- 双端候选、确认及正式卡片页面显示PDF页码、质量说明与可理解的错误。卡片生成仍使用MOCK，人工确认协议沿用D12。

## Web真实浏览器

使用仓库内[自制四页样本](../../tests/fixtures/d13-range-demo.pdf)，文件仅6242字节，无真实个人资料或外部文献。第1、4页含页段外标记，第2页含IN_RANGE_PAGE_TWO，第3页只有自制图片、没有文字层。样本第2页经渲染和文本核对。

1. 浏览器登录合成测试账号，通过实际上传页面保存资料#4；选择第2—3页提交任务#5。
2. 实际结果为4页总数、1页有效文字；来源#9标明PDF第2页，完整片段含第2页文字，不含第1、4页标记；第3页提示需要OCR或为空白页。
3. 在确认页修改摘要和卡片标题，保存卡片#4；正式卡片显示人工编辑、MOCK及来源版本1、第2页。
4. 再选择第3页提交任务#6，明确FAILED/PDF_OCR_REQUIRED，提取步骤失败，没有候选或假原文。

## 小程序页面真实HTTP与缓存复用

用实际小程序任务详情/确认页模块和本地HTTP适配器联调。任务#7、#8都基于资料#4版本2、选择第2—3页，复用同一来源chunkId #10。实际小程序页面显示PDF第2页，并通过确认接口保存卡片#5。WEB与MINIPROGRAM会话属于同一用户，读取卡片字段一致，保存来源pageNo=2。脱敏结果见[HTTP核对记录](D13-http-check.json)。本项包含真实后端及MySQL，不是微信开发者工具原生运行。

## 当前边界

- 尚未接入OCR、公有模型及受限智能体规划循环，不能据此声称真实AI分析质量或识别准确率。无文字层也可能是空白页，当前不区分扫描图与纯空白。
- 只提取可用文字层，不还原复杂版面、表格和页内图片文字。processedPages表示获得文字的页，不表示页内全部信息已被识别。
- 输出Writer有字符上限；PDFBox仍需在进程内解析所选页面，未实现独立进程的强制资源隔离。
- 微信原生编译、长按、真机网络和点击流程尚未验证；真实个人PDF及复杂中文排版样本后续补充，当前采用可复现的自制样本。
- 下一项D14：真实OCR适配；需先选定厂商并在本地提供调用配置。
